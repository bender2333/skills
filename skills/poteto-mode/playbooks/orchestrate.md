### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is **figure-it-out** (`skill://figure-it-out`). Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers with `task` (`skill://pstack-omp`). Keep the program's state in a durable `notes.md` file outside the repo (or in the repo if requested). Watch each PR with `skill://poteto-mode/playbooks/babysit.md` (`watch-pr`). Call no `orch` scripts, run no hand-rolled polling loops, and never relay raw status chatter between agents.

#### Topology

- **One owner per PR.** The owner (`owner` / `poteto-agent`) is the only writer of its branch and carries the PR from build to merge-ready. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full or shared via `local://<name>.md`. Workers can't see their siblings. Put each concurrent writer in its own worktree (`git worktree add`, or `isolated: true` when `task.isolation.enabled` is on), and note when a check needs local host hardware, transcripts, or auth. Pick each subagent's agent and effort per the Delegation section.
- **A sub-coordinator only when one area has many parallel workers.** Remember `task.maxRecursionDepth` defaults to 2, and `pstack-omp` treats leaves as non-delegating unless explicitly scoped; if a sub-coordinator prepares briefs, it returns them to the root to dispatch or stays within live `maxRecursionDepth`. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Message an existing worker only when new work needs its built state,** such as its checkout, uncommitted changes, or a running process, using `write agent://<id>`. Never message a worker just to check on it, because a message wakes an idle agent; inspect `agent://<id>`, `history://<id>`, or `read proc://<id>` instead.
- **Each PR gets a verifier that isn't its author,** on a different model family when configured (verified via returned resolved-model metadata). Merge only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a `eval` `browser` / `bash` PTY runtime check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or `origin pr` equivalents, not the worker's last report. Account for every worker you spawned (`agent://` / `proc://`) as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different agent/model after a tool error. After two retries, drop the unit and replan around it. Cancel stuck jobs with `write proc://<id>/kill`. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
